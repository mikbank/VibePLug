# Admin upload: invalid manifest

Status: **version 1.0.1 compatibility candidate; tenant acceptance pending**.

The original `niras-app-migration-1.0.0.zip` was reported rejected at Agents → Tools → All/Plugins → Upload with a generic invalid-manifest error. The service did not supply a specific failed rule in the available evidence.

## What was verified

Direct inspection of the original GitHub download found valid UTF-8 JSON, a root `manifest.json`, valid icons and all six declared skill folders. Microsoft's published Teams Manifest 0.1.9 and TeamsFx Core 3.1.5 libraries accepted its schema, skill inventory and portable transport preflight. The official `teamsApp/zipAppPackage` driver produced the same file set and identical nonmanifest bytes.

The absence of explicit ZIP directory entries was investigated. Microsoft's own packager produces the same layout, so no directory records were added as a speculative fix. Chat paste formatting and a briefly supplied manifest from a separate Copilot-created package were excluded from the diagnosis after the user corrected the input.

These results do **not** establish that Microsoft's admin service accepts the original ZIP, or identify its rejecting rule.

## Candidate 1.0.1

- Uses manifest **1.29**, the format currently generated by WIQD.
- Keeps app ID `261c64ae-e58d-4efa-aa5c-68907c8b3f46`, publisher/legal URLs and all six skills.
- Keeps package version `1.0.1` consistent with its filename.
- Adds Microsoft-library offline checks and an exact comparison of package contents with the official driver.
- Adds tests for malformed JSON whitespace, missing declared skills and schema/version consistency.

Download [dist/niras-app-migration-1.0.1.zip](dist/niras-app-migration-1.0.1.zip?raw=true) directly. Upload that ZIP without editing or repackaging it. Do not upload the source archive. Its SHA-256 is recorded in both `validation.json` and `microsoft-validation.json`.

## If the candidate is rejected

The next useful evidence is the service's validation details, if available, and any request/correlation ID with the time of the failed upload. The generic banner alone cannot identify the failed rule.

For an independent Microsoft service validation, use a signed-in machine with current WIQD:

```text
wiqd plugin validate --mode package --package-file ./dist/niras-app-migration-1.0.1.zip
```

This uploads a temporary copy of that exact ZIP to Teams Developer Portal for validation; it does not deploy the plugin. It may request Microsoft sign-in. Review the returned rule codes and report. Do not interpret `--mode source` passing as package acceptance.

Cowork's **Customize → Plugins → Upload plugin** is another documented ingestion route. If that accepts the same ZIP while admin upload rejects it, record both results before deciding the manifest is malformed. Organizational deployment still needs the appropriate admin scope/process.

No tenant policy, app registration, connector or permission has been changed during this investigation. No dummy agent or connector has been added merely to satisfy an unexplained validator error.
